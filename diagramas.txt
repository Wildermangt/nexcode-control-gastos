CONTENIDO

  ESTRUCTURA
  1. Arquitectura ................ capas, modulos e inversion de dependencias
  2. Infraestructura ............. despliegue: telefono, nube y protocolos
  3. Composicion ................. componentes internos e interfaces

  COMPORTAMIENTO
  4. Flujo: registrar un gasto ... del dedo del usuario a la nube
  5. Flujo: sincronizacion ....... una pasada completa, paso a paso
  6. Flujo: el agente de IA ...... llamada a funciones y cascada de modelos
  7. Flujo: arranque ............. actividad: sembrar o no sembrar

COMO IMPORTARLOS EN DRAW.IO

  1. Extras (o Arrange) -> Insert -> Advanced -> PlantUML...
  2. Copia UN diagrama, desde @startuml hasta @enduml. Pulsa Insert.
  3. Repite. draw.io inserta uno por vez.
  Para mover las cajas: seleccionar la imagen y Ctrl+Shift+U (desagrupar).

  SI DRAW.IO SE QUEJA DE LOS ICONOS
  Las lineas "!include <logos/...>" traen los logotipos que PlantUML incluye
  de fabrica. Si el servidor de draw.io fuera antiguo y no las resolviera,
  borra esas lineas y las etiquetas <$...> del diagrama: todo lo demas sigue
  funcionando igual. La alternativa es usar directamente las imagenes ya
  exportadas en recursos/diagramas/ (PNG y SVG).

SIMBOLOS

  telefono   nodo fisico donde corre la aplicacion
  nube       servicio alojado fuera del telefono
  cilindro   almacen persistente (SQLite en el telefono, Firestore en la nube)
  logo       tecnologia concreta: Firebase, Android, SQLite, Kotlin, Java
  []         componente UML          ()   interfaz
  ..|>       realizacion (implementa)  ..>  dependencia (usa)

skinparam backgroundColor #FFFFFF

skinparam defaultFontSize 12
skinparam roundCorner 6

participant "<$firebase>\nCloud Firestore" as FS #E9F7EF

autonumber "<b>0."
W -> M : sincronizar()
activate M

M -> A : uid de la sesion
alt sesion disponible
  A --> M : uid
else sin red o sin proveedor habilitado
  A --> M : null
  M --> W : SinSesion\n"Sin conexion, tus datos siguen en el telefono"
  note right of M
    La aplicacion **no se cae** ni pierde nada:
    Room sigue siendo la fuente de verdad.
    Este es el peor caso de la redundancia,
    y funciona.
  end note
end

group 1 · Subida de todo lo pendiente
  M -> DB : pendientes de las 4 tablas
  M -> FS : lote de escritura\n(los borrados logicos suben tambien)
  FS --> M : confirmado
  M -> DB : marcar sincronizado = 1
end

group 2 · Bajada del catalogo
  M -> FS : cuentas y categorias\nactualizado_en > ultima marca
  FS --> M : documentos nuevos
  M -> DB : insertar o actualizar por uuid
end

group 3 · Reconstruir la traduccion de identificadores
  M -> DB : releer uuid <-> id local
  note right of M
    **No es adorno.** El paso 2 pudo crear cuentas
    nuevas en esta base. Sin rehacer la tabla de
    equivalencias, los movimientos bajarian
    apuntando a identificadores que ya no valen.
  end note
end

group 4 · Bajada de lo que depende del catalogo
  M -> FS : movimientos y pagos fijos
  FS --> M : documentos nuevos
  M -> DB : insertar o actualizar
  note right of M
    Un movimiento cuya cuenta aun no bajo **no se
    descarta**: espera a la siguiente pasada. La
    marca solo avanza sobre lo aplicado, asi que
    un corte a mitad se reanuda donde quedo.
  end note
end

M --> W : Exito(subidos, bajados)
deactivate M

database "<$sqlite>\nRoom" as DB #FDF3E3
participant "Gemini API" as API #E9F7EF

autonumber "<b>0."
U -> S : "cuanto llevo gastado este mes?"
S -> UC : pedirConsejo(pregunta)
activate UC
UC -> G : responder(pregunta, herramientas)
activate G

note right of G
  El mensaje inicial **no lleva** el estado financiero
  a proposito. Si se le entregara masticado, el modelo
  no tendria motivo para usar las herramientas y
  dejaria de ser un agente.
end note

G -> API : generateContent\n+ declaracion de 5 funciones
alt 503 "high demand"
  API --> G : modelo saturado
  G -> G : **cambia de modelo**\nflash-latest -> 3.7-flash -> flash-lite
  G -> API : reintento con el siguiente
end
API --> G : functionCall: consultar_resumen_del_mes

loop mientras el modelo siga pidiendo funciones
  G -> T : ejecutar(nombre, argumentos)
  activate T
  T -> DB : consulta real sobre los datos
  DB --> T : ingresos, gastos, reparto
  T --> G : resultado en JSON
  deactivate T
  G -> API : functionResponse\n+ thoughtSignature devuelta intacta
  API --> G : otra funcion, o la respuesta final
end

API --> G : texto final
G --> UC : respuesta
deactivate G
UC --> S : respuesta
deactivate UC
S --> U : "Llevas $226.600. Mercado 39%, Ocio 14%..."

note over G, API
  Se habla **REST directo**, sin el SDK. Dos motivos comprobados en
  dispositivo: el SDK manda el rol "function" que la API rechaza con
  400, y no modela el thoughtSignature que los modelos 3.x exigen de
  vuelta, con lo que la conversacion moria en el segundo turno.
  Ademas quito 4 MB del APK.
end note

7. FLUJO - Arranque de la aplicacion: sembrar o no sembrar

@startuml Nexcode-7-Flujo-Arranque
title Flujo · Arranque: la decision que evitaba duplicar los datos

skinparam backgroundColor #FFFFFF
skinparam shadowing false
skinparam defaultFontName Segoe UI
skinparam defaultFontSize 12
skinparam roundCorner 6
skinparam ArrowColor #35506B

start
:NexcodeApplication.onCreate();
:Construir AppContainer;
:Crear canal de notificaciones;

if (¿Firebase inicializo?\n(hay google-services.json)) then (no)
  :Motor de replica = null;
  note right
    La aplicacion opera **solo contra Room**,
    exactamente como antes de tener nube.
    Sin este camino, la falta de configuracion
    romperia la entrega.
  end note
  :Sembrar datos de demostracion;
else (si)
  :Preguntar a la nube:\n¿este usuario ya tiene cuentas?\n(Source.SERVER, tope de 12 s);

  if (respuesta) then (la nube TIENE datos)
    :**No sembrar nada**;
    note right
      Sembrar aqui era el error: el telefono nuevo
      creaba sus 10 cuentas y ademas bajaba las 10
      de la nube. 20 cuentas duplicadas, y lo mismo
      con las otras tres tablas.
    end note
  else (vacia, o no se pudo saber)
    :Sembrar 10 cuentas, 10 categorias,\n10 movimientos y 10 pagos fijos;
    :uuid **fijo** derivado del nombre\n(demo-cuenta-efectivo)\ny fecha fija en el pasado;
    note right
      El uuid fijo hace inofensiva una siembra a
      ciegas: si la nube ya tenia esas filas, la
      bajada las **actualiza** en vez de anadirlas.
      La fecha en el pasado impide que la semilla
      pise una edicion del usuario.
    end note
