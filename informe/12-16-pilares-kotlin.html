12

Aplicación de estructuras, arreglos y ciclos

Nexcode trabaja con dos estructuras de datos principales. La lista (List) representa secuencias ordenadas —los movimientos de un mes, los pagos fijos del bolsillo, las categorías disponibles— y la tabla asociativa (Map) representa búsquedas por clave, sobre todo el índice de categorías por identificador que evita recorrer la lista completa cada vez que una fila de la interfaz necesita saber a qué categoría pertenece.

El recorrido de esas estructuras se resolvió con funciones de orden superior en lugar de ciclos for manuales. La razón no es estética: un ciclo manual mezcla en un mismo bloque el recorrido, el filtrado, la acumulación y la construcción del resultado, mientras que la versión declarativa nombra cada operación por separado y hace visible la intención. Los ciclos explícitos se reservan para el caso contrario —generar una colección que no existe— y el apartado C reúne los dos que hay en todo el proyecto. La Tabla VII lista las funciones empleadas.

A. Caso representativo: reparto del gasto por categoría

La función que alimenta el gráfico de dona concentra la mayoría de estas operaciones. Recibe una lista de movimientos y un mapa de categorías, y devuelve una lista ordenada de resúmenes. Nótese que no aparece ningún ciclo explícito:

fun summarize(
    transactions: List<Transaction>,
    categoriesById: Map<Long, Category>
): List<CategorySummary> {
    val expenses = transactions.filter { it.type is TransactionType.Expense }
    if (expenses.isEmpty()) return emptyList()

    val grandTotal: Long = expenses.sumOf { it.amount.cents }
    if (grandTotal == 0L) return emptyList()

    return expenses
        .groupBy { it.categoryId }                       // Map<Long?, List<Transaction>>
        .map { (categoryId, items) ->
            val total = items.sumOf { it.amount.cents }
            CategorySummary(
                category = categoryId?.let { categoriesById[it] },   // safe call
                total = Money(total),
                transactionCount = items.size,
                percentage = total.toFloat() / grandTotal.toFloat()
            )
        }
        .sortedByDescending { it.total.cents }
}

Fragmento 1. domain/usecase/analytics/GetCategorySummaryUseCase.kt — cinco operaciones encadenadas: filtrar, sumar, agrupar, transformar y ordenar.

La cadena se lee de arriba abajo como una frase: de los movimientos, tomar los gastos, agruparlos por categoría, convertir cada grupo en un resumen y ordenarlos de mayor a menor. Un ciclo for equivalente necesitaría un acumulador mutable, una condición interna y una estructura auxiliar, y sería más difícil de probar de forma aislada. Esta función es pura —no consulta la base de datos— y por eso tiene cinco pruebas unitarias propias.

B. Acumulación con lógica propia

Cuando la acumulación no es una suma simple se recurre a fold, que recibe un valor inicial y decide en cada paso qué hacer. El saldo neto de un día debe ignorar las transferencias entre cuentas propias, porque no alteran el patrimonio total:

private fun netTotal(transactions: List<Transaction>): Money =
    transactions.fold(Money.ZERO) { acc, transaction ->
        when (transaction.type) {
            is TransactionType.Transfer -> acc          // no altera el saldo
            else -> acc + transaction.signedAmount
        }
    }

C. Los dos ciclos explícitos del proyecto

Hay dos lugares en los que un ciclo sí es la herramienta correcta, y comparten un mismo rasgo: en ninguno de los dos se recorre una colección que ya existe, sino que se construye una que todavía no existe. El primero busca la próxima fecha en que caerá un día de la semana determinado. El recorrido va sobre fechas generadas y termina por una condición, así que se acotó deliberadamente con repeat(7) para que sea imposible que no termine:

private fun nextWeekly(after: LocalDate, dayOfWeek: Int): LocalDate {
    var candidata = after.masDias(1)
    // Ciclo acotado: como maximo siete intentos.
    repeat(7) {
        if (candidata.dayOfWeek.isoDayNumber == dayOfWeek) return candidata
        candidata = candidata.masDias(1)
    }
    return candidata
}

Fragmento 3. domain/model/RecurringFrequency.kt — ciclo con cota superior demostrable: en siete días siempre aparece cualquier día de la semana.

El segundo construye el eje de meses de la analítica del gasto, y es el que mejor separa las dos herramientas, porque las usa a las dos seguidas y por motivos opuestos. La agregación de los movimientos —una colección que ya existe— se resuelve con groupBy; la serie de meses —que no existe en ninguna parte— se genera con un for sobre el calendario:

// Recorrido de una coleccion que YA existe: funcion de orden superior.
val porMes: Map<MesDelAnio, List<Transaction>> =
    transactions.groupBy { MesDelAnio.de(it.dateTime) }

// CICLO EXPLICITO. Aqui no se recorre una coleccion: se GENERA una.
// La cota superior es demostrable: exactamente `meses` vueltas.
val serie = ArrayList<PuntoMensual>(meses)
var cursor: LocalDate = hoy.primerDiaDelMes().menosMeses(meses - 1)

for (i in 0 until meses) {
    val mes = MesDelAnio.de(cursor)
    // orEmpty(): un mes sin movimientos vale una lista vacia, no null.
    val delMes = porMes[mes].orEmpty()
    val balance = balanceCalculator.calculate(delMes)

    serie.add(
        PuntoMensual(
            mes = mes,
            ingresos = balance.income,
            gastos = balance.expense,
            movimientos = delMes.size
        )
    )
    cursor = cursor.masMeses(1)
}

Fragmento 4. domain/usecase/analytics/AnalizarTendenciaUseCase.kt — las dos herramientas juntas: groupBy para recorrer lo que hay, for para generar lo que falta.

La razón por la que el ciclo no puede sustituirse aquí por otra cadena de funciones merece detenerse, porque es el argumento que justifica la excepción. Un groupBy devuelve únicamente los meses que tienen movimientos: si el usuario no gastó nada en julio, julio no aparece en el mapa. La serie quedaría con cuatro meses donde debe haber seis, las barras del gráfico se correrían de sitio y la comparación con el mes anterior compararía contra el mes equivocado. Y el mes vacío es justamente el dato que más dice. Por eso el ciclo recorre el calendario y consulta los datos, y no al revés: el eje del análisis lo fija el tiempo, no lo que haya en la base de datos.

Criterio adoptado

Se usan funciones de orden superior para recorrer colecciones existentes y ciclos explícitos únicamente cuando se generan valores nuevos. En este último caso el ciclo lleva siempre una cota superior demostrable: siete intentos en el Fragmento 3, tantas vueltas como meses pida la ventana en el Fragmento 4.

A. Encapsulamiento: objetos que no pueden nacer inválidos

En lugar de validar desde fuera antes de construir un objeto, cada modelo protege sus propias invariantes en el constructor. Si alguna condición no se cumple, la instancia no llega a existir:

data class Transaction(
    val id: Long = 0L,
    val accountId: Long,
    val categoryId: Long? = null,
    val type: TransactionType,
    val amount: Money,
    val dateTime: LocalDateTime,
    val title: String,
    val note: String? = null
) {
    init {
        require(amount.isPositive) { "El monto debe ser mayor que cero" }
        require(title.isNotBlank()) { "El titulo no puede estar vacio" }
        require(accountId > 0L) { "La transaccion debe pertenecer a una cuenta valida" }
    }

    /** Monto con signo contable: -50.000 para un gasto. */
    val signedAmount: Money get() = type.applySign(amount)
}

Fragmento 5. domain/model/Transaction.kt — atributos inmutables, invariantes verificadas en la construcción y un método derivado.

Todos los atributos se declaran val, es decir, de solo lectura. Modificar una transacción no muta el objeto sino que produce uno nuevo mediante copy(), lo que elimina toda una familia de errores por estado compartido. Una decisión de diseño relacionada es que el monto es siempre positivo y el signo contable lo aporta el tipo: guardar montos negativos para los gastos es una fuente clásica de errores de cuadre.

B. Herencia y polimorfismo mediante jerarquías selladas

El tipo de movimiento es una jerarquía de herencia: una clase base abstracta con tres subclases. Al declararla sealed, el compilador conoce la lista completa de subtipos, de modo que una expresión when sobre ella es exhaustiva y no necesita rama else. Si mañana se agregara un cuarto tipo de movimiento, el compilador señalaría todos los lugares donde falta contemplarlo.

sealed class TransactionType(
    val code: String,
    val sign: Int
) {
    data object Income   : TransactionType(code = "INCOME",   sign = +1)
    data object Expense  : TransactionType(code = "EXPENSE",  sign = -1)
    data class  Transfer(val targetAccountId: Long)
                         : TransactionType(code = "TRANSFER", sign =  0)

    /** Aplica el signo contable al monto. */
    fun applySign(amount: Money): Money = Money(amount.cents * sign)

    fun defaultTitle(): String = when (this) {
        is Income   -> "Ingreso"
        is Expense  -> "Gasto"
        is Transfer -> "Transferencia"
    } // sin `else`: la sealed class garantiza exhaustividad
}

Fragmento 6. domain/model/TransactionType.kt — herencia sellada. Income y Expense son objetos únicos porque no llevan datos propios; Transfer es una clase porque necesita la cuenta destino.

El polimorfismo se manifiesta en que applySign produce un resultado distinto según el subtipo sin necesidad de condicionales: cada subclase aporta su propio sign al constructor de la clase base. La Fig. 5 muestra las dos jerarquías selladas del proyecto.

C. Objetos de valor: el dinero como tipo propio

Un importe no es un número cualquiera: no tiene sentido multiplicar dos importes entre sí, y sumar pesos con centavos por descuido produce errores silenciosos. Por eso el dinero se modela como una clase propia que envuelve un entero de centavos y expone únicamente las operaciones que tienen sentido, mediante sobrecarga de operadores:

@JvmInline
value class Money(val cents: Long) : Comparable<Money> {
    val isPositive: Boolean get() = cents > 0

    operator fun plus(other: Money): Money  = Money(cents + other.cents)
    operator fun minus(other: Money): Money = Money(cents - other.cents)
    operator fun unaryMinus(): Money        = Money(-cents)

    override fun compareTo(other: Money): Int = cents.compareTo(other.cents)

    /** Formato colombiano en pesos enteros: 1.250.000 */
    fun format(withSign: Boolean = false): String { /* ... */ }
}

Manejo de excepciones

La estrategia adoptada parte de una regla: las excepciones no cruzan hacia la capa de presentación. Una pantalla no debe envolver llamadas en bloques try; debe recibir un estado y pintarlo. Para lograrlo, el manejo de errores se organiza en tres niveles sucesivos.

A. Nivel 1: conversión de texto a número

El punto más frágil de la aplicación es la conversión del texto que escribe el usuario a un valor numérico. Se resuelve con un try que captura las dos excepciones que la biblioteca estándar puede lanzar y las convierte en una excepción propia del dominio, conservando la causa original:

return try {
    Money(
        BigDecimal(normalized)
            .movePointRight(2)
            .setScale(0, RoundingMode.HALF_UP)
            .toLong()
    )
} catch (e: NumberFormatException) {
    throw InvalidAmountException("\"" + raw + "\" no es un monto valido", e)
} catch (e: ArithmeticException) {
    throw InvalidAmountException("El monto \"" + raw + "\" excede el limite permitido", e)
}

Fragmento 8. domain/model/Money.kt — la excepción original viaja como cause, de modo que no se pierde información para la depuración.

B. Nivel 2: traducción a resultados

El caso de uso envuelve toda su lógica en un único bloque try y declara seis capturas ordenadas de la más específica a la más general. Cada una produce una variante distinta del resultado:

// MANEJO DE EXCEPCIONES: de la mas especifica a la mas general.
} catch (e: InvalidAmountException) {
    AddTransactionResult.InvalidAmount(e.message ?: "Monto invalido")
} catch (e: BlankFieldException) {
    AddTransactionResult.MissingField(e.fieldName)
} catch (e: AccountNotFoundException) {
    AddTransactionResult.NotFound(e.message ?: "Cuenta no encontrada")
} catch (e: CategoryNotFoundException) {
    AddTransactionResult.NotFound(e.message ?: "Categoria no encontrada")
} catch (e: IllegalArgumentException) {
    // Disparada por los require() del modelo de dominio.
    AddTransactionResult.MissingField(e.message ?: "Datos incompletos")
} catch (e: Exception) {
    // Red de seguridad: fallo de Room, disco lleno, etc.
    AddTransactionResult.Failure(
        "No se pudo guardar la transaccion: " + (e.message ?: "error desconocido")
    )
}

Seguridad contra valores nulos

Kotlin distingue en el sistema de tipos entre una referencia que puede ser nula (String?) y una que no (String). El compilador impide llamar a un método sobre la primera sin haber comprobado antes su contenido, lo que elimina en tiempo de compilación la excepción de puntero nulo.

En Nexcode la nulabilidad no se usa por comodidad sino que modela hechos del negocio. Un movimiento puede no tener categoría, porque la política ON DELETE SET NULL del esquema deja huérfanos los movimientos cuando se borra una categoría; una nota es opcional porque el usuario no está obligado a escribirla; un presupuesto mensual puede no existir. El operador !! no se usa en ninguna de las 6 548 líneas del proyecto. Ese operador desactiva la comprobación del compilador y reintroduce exactamente el fallo que el sistema de tipos evita; cada caso en que fue tentador se resolvió con Elvis o con una llamada segura.

B. Caso representativo: cadena de respaldos

El fragmento más ilustrativo está en el caso de uso de registro. El título del movimiento se resuelve con una cadena de tres niveles: lo que escribió el usuario, si no está en blanco; en su defecto el nombre de la categoría; y si tampoco hay categoría, el título por defecto del tipo de movimiento. La expresión no puede producir nulo:

    ?: throw AccountNotFoundException(input.accountId)

// 3. Categoria: safe call. Si categoryId es null NO se consulta la base.
val category: Category? = input.categoryId?.let { id ->
    categoryRepository.findById(id) ?: throw CategoryNotFoundException(id)
}

// 4. Titulo: cadena de Elvis con tres niveles de respaldo.
val title: String = input.rawTitle?.trim()?.takeIf { it.isNotBlank() }
    ?: category?.name
    ?: input.type.defaultTitle()

// 5. Nota opcional: "   " se normaliza a null, no a cadena vacia.
val note: String? = input.rawNote?.trim()?.takeIf { it.isNotBlank() }

Fragmento 10. domain/usecase/transaction/AddTransactionUseCase.kt — cuatro usos distintos de la seguridad ante nulos en doce líneas.

Tres detalles merecen comentario. Primero, ?: throw aprovecha que en Kotlin throw es una expresión, lo que permite obtener un valor no nulo o interrumpir en una sola línea. Segundo, la llamada segura sobre categoryId evita una consulta innecesaria a la base de datos cuando no hay categoría. Tercero, la combinación ?.trim()?.takeIf { it.isNotBlank() } normaliza a nulo una nota compuesta solo de espacios, de modo que la base de datos nunca almacena cadenas en blanco que después obliguen a comprobar dos condiciones distintas.

Del lado de la lectura, los modelos exponen propiedades derivadas que entregan a la interfaz un valor siempre seguro, como val displayNote: String get() = note ?: "Sin nota". La pantalla no comprueba nulos: recibe texto listo para pintar.

A. Fallo 3: el error de lógica que atrapó una prueba

Es el caso más instructivo porque no produjo ningún mensaje de error: la aplicación funcionaba y guardaba un valor incorrecto. Al escribir 25.000 —veinticinco mil pesos en notación colombiana— el sistema almacenaba 25 pesos, porque la regla original interpretaba un punto único como separador decimal.

El fallo se detectó al escribir la prueba unitaria del caso de uso de registro, antes de que ningún usuario tocara la aplicación. La corrección consistió en formalizar la regla de notación:

val lastComma = text.lastIndexOf(',')
val lastDot   = text.lastIndexOf('.')
val digitsAfterLastDot = if (lastDot >= 0) text.length - lastDot - 1 else -1

val normalized = when {
    // Hay coma: la coma manda como decimal y los puntos son miles.
    lastComma >= 0 -> text.replace(".", "").replace(',', '.')
    // Solo puntos, el ultimo con 3 digitos detras: separador de miles.
    lastDot >= 0 && digitsAfterLastDot == 3 -> text.replace(".", "")
    // Resto de casos: el punto es el separador decimal.
    else -> text
}

B. Fallo 2: el compilador como detector de fallas de arquitectura

Al conectar la interfaz con la base de datos, el módulo de presentación dejó de compilar con un mensaje que a primera vista parecía un problema de dependencias:

e: AppContainer.kt:45:44 Cannot access 'androidx.room.RoomDatabase'
   which is a supertype of 'NexcodeDatabase'.
   Check your module classpath for missing or conflicting dependencies.

El diagnóstico correcto no era agregar Room como dependencia de la capa de presentación —eso habría hecho desaparecer el error y, con él, la separación de capas— sino reconocer que el mensaje señalaba una fuga arquitectónica: la presentación estaba construyendo la base de datos. La solución fue mover ese ensamblaje al interior de la capa de datos, tras la fábrica DataProvider. El error desapareció y la arquitectura quedó más estricta que antes.

C. Fallo 5: descartar un falso positivo

Al probar el borrado por deslizamiento mediante automatización, la aplicación desaparecía de la pantalla y quedaba visible otra aplicación. La hipótesis inicial fue un fallo grave en el componente de deslizamiento. La inspección de la captura mostró que la aplicación visible era otro proyecto del mismo equipo, lo que descartaba un cierre por error: el gesto de prueba, iniciado en el borde derecho de la pantalla, había activado el gesto «atrás» del sistema operativo. Al repetir el mismo gesto lejos del borde, el borrado funcionó correctamente. El fallo estaba en el método de prueba, no en el código.
