Proyecto Integrador · Sección 17

Multiplataforma en Nexcode

Migración de la capa de dominio a Kotlin Multiplatform, y qué se descubrió al compilarla para una plataforma que no es la JVM

Autores Jeferson Wilderman González Tenjo José Leandro Ocampo Camacho
Programa Ingeniería de Sistemas Universidad de San Buenaventura
Asignatura Optativa II — Desarrollo Móvil Sexto semestre, 2026
Objetivos compilados JVM (Android y escritorio) JavaScript (Node.js)

Resumen — La capa de dominio de Nexcode se migró de un módulo Kotlin/JVM a un módulo Kotlin Multiplatform con dos objetivos de compilación: JVM y JavaScript. La migración obligó a eliminar del dominio toda dependencia de la biblioteca estándar de Java —BigDecimal, java.time y java.util— y a sustituir el acceso al reloj del sistema por una abstracción inyectable. El resultado se verifica ejecutando las mismas 41 pruebas unitarias en las dos plataformas. El hallazgo más relevante no fue el resultado sino el proceso: dos acoplamientos a Java que ninguna revisión manual había detectado se hicieron visibles en el momento de compilar para JavaScript.

Implementación multiplataforma

La Sección 11 sostiene que la capa de dominio está aislada del framework. Esa afirmación se apoyaba en una prueba negativa: no aparecen imports de Android en sus archivos. Es una evidencia razonable, pero indirecta; un módulo puede estar libre de Android y seguir atado a la plataforma por la vía de la biblioteca estándar de Java, que en Android está disponible y por tanto no produce ningún error.

La prueba concluyente de que una capa es independiente de la plataforma consiste en compilarla para otra. Con esa finalidad se migró el módulo :domain a Kotlin Multiplatform.

A. Qué significa multiplataforma en este proyecto

Kotlin Multiplatform permite escribir código una sola vez en un conjunto de fuentes común y compilarlo para varios destinos. El conjunto commonMain no tiene acceso a la biblioteca de Java ni a las API de ninguna plataforma concreta: solo a la biblioteca estándar de Kotlin y a bibliotecas que a su vez sean multiplataforma. Esa restricción no la impone una convención del equipo, la impone el compilador.

Se eligieron dos objetivos. JVM, porque es el que consumen el módulo :data y la aplicación Android. Y JavaScript sobre Node.js, porque es una plataforma genuinamente distinta —no comparte biblioteca estándar con Java— y por tanto sirve como verificación real de portabilidad. La Fig. 8 muestra la estructura resultante.

La sustitución del reloj merece un comentario aparte porque no fue solo un cambio de biblioteca. El caso de uso de registro llamaba directamente a LocalDateTime.now(), lo que ataba el dominio a la plataforma y hacía imposible escribir una prueba que verificara la fecha guardada. Al reemplazarlo por una interfaz inyectable de una sola función, ambos problemas desaparecieron a la vez:

// commonMain — el dominio declara lo que necesita, no cómo se obtiene
fun interface RelojDominio {
    fun ahora(): LocalDateTime
}

// :app — la plataforma cumple el contrato
class RelojSistema : RelojDominio {
    override fun ahora(): LocalDateTime =
        java.time.LocalDateTime.now().toKotlinLocalDateTime()
}

// commonTest — la prueba fija el tiempo
val RELOJ_FIJO = RelojDominio { LocalDateTime(2026, 8, 22, 12, 0) }

C. Los acoplamientos que solo el compilador de JavaScript reveló

Este es el resultado más útil de la migración. Tras retirar las dieciséis referencias de la Tabla XVI, el módulo compilaba sin errores para JVM. Se habría podido concluir que el trabajo estaba terminado. Sin embargo, al compilar para JavaScript aparecieron dos errores más:

$ ./gradlew :domain:compileKotlinJs

e: Money.kt:16:2  Unresolved reference 'JvmInline'.
e: GetTransactionsUseCase.kt:29:18  Unresolved reference 'toSortedMap'.

BUILD FAILED

El primero es sutil: @JvmInline es obligatorio para declarar una value class, y en un módulo JVM el compilador lo resuelve automáticamente. En código común no: exige el import explícito kotlin.jvm.JvmInline, porque es una anotación de expectativa opcional que cada plataforma implementa a su manera.

El segundo es más grave desde el punto de vista arquitectónico. La función toSortedMap parece Kotlin idiomático —se encadena igual que map o filter— pero pertenece a java.util.SortedMap. Estaba en medio de una cadena de operaciones de colecciones, sin ningún import que la delatara, y ninguna revisión manual la había detectado. La corrección fue reescribir la operación con funciones de la biblioteca estándar de Kotlin:

// Antes: toSortedMap viene de java.util, invisible en la cadena
transactions
    .groupBy { it.day }
    .toSortedMap(compareByDescending { it })
    .mapValues { entry -> entry.value.sortedByDescending { it.dateTime } }

// Después: solo biblioteca estándar de Kotlin
transactions
    .groupBy { it.day }
    .toList()
    .sortedByDescending { (dia, _) -> dia }
    .associate { (dia, movimientos) ->
        dia to movimientos.sortedByDescending { it.dateTime }
    }

Fragmento 14. domain/usecase/transaction/GetTransactionsUseCase.kt — la versión portable produce el mismo resultado: associate conserva el orden de inserción.

Hallazgo

Dos acoplamientos a la plataforma sobrevivieron a la revisión manual y a la compilación para JVM, y solo se hicieron visibles al compilar para JavaScript. Esto sustenta la tesis de la sección: la independencia de plataforma no se declara, se comprueba compilando para otra. Un módulo que solo se compila para su destino habitual puede estar acoplado sin que nadie lo note.

D. Dónde ocurre la traducción entre mundos

El dominio dejó de hablar java.time, pero las capas que lo rodean sí lo necesitan: Room almacena las fechas, y DateTimeFormatter es lo que sabe escribir «Sábado 22 de agosto» en español. La conversión entre ambos sistemas de tipos se concentró deliberadamente en cinco archivos frontera, listados en la Tabla XVII. Fuera de ellos, ningún archivo del proyecto mezcla los dos mundos.

E. Qué se comparte y qué no puede compartirse

Conviene delimitar el alcance con precisión, porque «multiplataforma» admite lecturas más amplias que la que aplica aquí. Lo compartido es la capa de dominio completa: modelos, reglas de validación, casos de uso, cálculos y contratos. Lo que no se comparte es todo aquello que por definición depende del sistema operativo, y la Tabla XVIII lo enumera sin eufemismos.

F. Verificación

La prueba de que la migración cumplió su objetivo es que el mismo archivo de pruebas se ejecuta en las dos plataformas y produce el mismo resultado. No se trata de dos suites paralelas: es un único conjunto en commonTest, compilado dos veces.

$ ./gradlew :domain:jvmTest :domain:jsNodeTest

jvmTest    · MoneyTest ....................... 12 pruebas, 0 fallos
jvmTest    · AddTransactionUseCaseTest ......  7 pruebas, 0 fallos
jvmTest    · GetCategorySummaryUseCaseTest ..  5 pruebas, 0 fallos

jsNodeTest · MoneyTest ....................... 12 pruebas, 0 fallos
jsNodeTest · AddTransactionUseCaseTest ......  7 pruebas, 0 fallos
jsNodeTest · GetCategorySummaryUseCaseTest ..  5 pruebas, 0 fallos

BUILD SUCCESSFUL

Que las pruebas de Money pasen en JavaScript tiene un valor añadido: el análisis de montos se reescribió sin BigDecimal, y JavaScript no tiene enteros de 64 bits nativos —Kotlin los emula—. Que el redondeo al centavo produzca el mismo resultado en ambas plataformas confirma que la reimplementación es correcta y no solo compilable.

G. Limitaciones y trabajo futuro

El alcance alcanzado es real pero acotado, y conviene declararlo con la misma claridad con que se declara el logro.

No hay objetivo iOS. Compilar para iOS exige un equipo con macOS y las herramientas de Xcode, de las que el equipo no dispone. La restricción es de infraestructura, no de diseño: el código de commonMain no usa nada que impida añadir ese objetivo, y hacerlo consistiría en declararlo en el archivo de construcción.

La interfaz no se comparte. Nexcode tiene una sola interfaz, escrita en Jetpack Compose para Android. Compartirla exigiría migrar a Compose Multiplatform, que es un proyecto de otra magnitud y no formaba parte de los objetivos.

El objetivo JavaScript no tiene consumidor. Existe como verificación, no como producto: no hay una versión web de Nexcode. Su valor es el descrito en el apartado C, y ese valor se cobra en cada compilación futura, porque cualquier acoplamiento nuevo a la plataforma romperá el build.

Costo asumido

La migración tuvo un precio que conviene registrar: el dominio ya no usa BigDecimal, de modo que el análisis de montos es código propio y no una biblioteca probada por terceros. Se compensó con ocho pruebas unitarias específicas de Money, incluidas las de redondeo del tercer decimal y de límite superior. Es un intercambio consciente: se cambió una dependencia de plataforma por código propio bajo prueba.

H. Conclusión

La migración confirmó la afirmación de la Sección 11 y, a la vez, mostró que la evidencia en que esa afirmación se apoyaba era insuficiente. Contar imports de Android detecta el acoplamiento evidente; compilar para otra plataforma detecta el acoplamiento silencioso. Los dos errores del apartado C llevaban semanas en el repositorio sin que ninguna herramienta anterior los señalara.

El resultado práctico es que la lógica de negocio de Nexcode —qué hace válido un gasto, cómo se reparte el gasto por categoría, cuándo vence un pago fijo— es hoy código portable, verificado en dos plataformas, que podría reutilizarse en una versión web o de escritorio sin reescribir una línea.
